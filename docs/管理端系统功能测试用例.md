## 0. 执行者阅读顺序（先看这一页）

### 0.1 三阶段工作流

```
阶段一  执行测试
  ├─ 0. 环境自检（第 2 章）
  ├─ 1. 冒烟测试（附录 C，约 15 分钟）
  ├─ 2. 按第 4 章用例逐条执行（P0 → P1 → P2）
  └─ 3. 每条用例填写「实际结果 + 证据路径 + 结论」
            ↓
阶段二  记录问题
  ├─ 1. 用第 5.1 节模板写缺陷单（一条问题一张单）
  ├─ 2. 定严重等级（5.2）、定优先级、去重（5.4）
  └─ 3. 汇总为缺陷清单（5.6）
            ↓
阶段三  写测试报告
  ├─ 1. 用第 6.1 节模板填写
  ├─ 2. 用第 6.2 节公式算执行率 / 通过率 / 缺陷密度
  ├─ 3. 按第 6.3 节给出版本结论（可发布 / 有条件发布 / 不可发布）
  └─ 4. 附用例明细、缺陷清单、证据索引
```

### 0.2 最小执行集（时间不够时）

只执行所有 **P0** 用例 + 每个模块至少 1 条 **P1** 用例。P0 未全部通过时，不出具「通过」结论。

### 0.3 禁止事项

1. 不要在**生产环境**（如 `8.138.171.50`）执行增删改类用例；只允许在本地或专用测试环境执行。
2. 不要删除 `admin` 自身账号、当前学期、系统预置班级/课程。
3. 不要为了通过用例而修改数据库；数据库只用于**核对**，不用于**造结果**。
4. 不要提交真实密钥、真实学生隐私数据到测试报告。
5. AI 类用例（课程导入、AI 出题、章节一键生成、作息图片识别）依赖 `DEEPSEEK_API_KEY` 与向量服务；环境未就绪时标记 `BLOCKED`，不要判产品 FAIL。

## 1. 测试目标、范围与策略

### 1.1 测试目标

1. 验证管理员可完成「人员 → 学期 → 课程 → 排课 → 作息 → 日常审批 → 教学数据」的完整管理闭环。
2. 验证管理员 / 教师 / 学生三种角色的菜单与接口权限隔离正确。
3. 验证关键写操作的数据一致性（页面结果 = 数据库结果 = 其他页面可见结果）。
4. 验证异常输入、网络异常、权限异常下有友好提示且不白屏、不产生脏数据。
5. 产出一份可复现、可统计、可评审的测试报告。

### 1.2 测试范围

| 范围内 | 说明 |
|---|---|

## 3. 用例执行规范

### 3.1 单条用例记录模板

每条用例执行后填写：

| 字段 | 填写要求 |
|---|---|
| 用例编号 | 如 `T-04` |
| 执行时间 | `2026-11-08 14:32` |
| 执行人 | 姓名或模型标识 |
| 实际结果 | 客观描述看到的现象，不写「正常/不正常」 |
| 结论 | PASS / FAIL / BLOCKED / SKIP |
| 证据 | 截图/HAR/接口响应/SQL 结果路径 |
| 缺陷编号 | FAIL 时填写 `BUG-001` |
| 备注 | 环境、账号、数据等补充 |

### 3.2 结果状态定义

| 状态 | 定义 |
|---|---|
| PASS | 实际结果与预期完全一致，且数据一致性核对通过 |
| FAIL | 功能错误、数据错误、权限错误、崩溃、白屏、提示缺失 |
| BLOCKED | 环境/账号/AI 服务/测试数据缺失，无法执行 |
| SKIP | 明确不在本次范围，或不具备条件且不影响结论 |

> 不允许把「功能没做完」记为 PASS；没做完记 FAIL 或 BLOCKED，并在缺陷单注明「功能缺失」。

### 3.3 证据规范

| 场景 | 必须提供的证据 |
|---|---|
| 页面展示错误 | 全屏截图 + 浏览器宽度 |
| 提示错误/无提示 | 截图 + Console/Network |
| 接口错误 | 请求 URL、方法、请求体、状态码、响应体 |
| 数据不一致 | 页面截图 + SQL 查询与结果 |
| 权限问题 | 当前账号角色 + 请求响应 403/200 + 页面截图 |
| 偶现问题 | 复现次数/尝试次数 + 录屏或连续截图 |
| 性能问题 | Network 时序、接口耗时、页面可交互时间 |

### 3.4 缺陷 / 环境 / 需求三分类

| 分类 | 判定 |
|---|---|
| 产品缺陷 | 预期明确、可稳定复现、由代码/配置导致 |
| 环境问题 | 后端未启动、数据库缺表、AI key 缺失、端口占用、浏览器缓存 |
| 需求变更 | 实现与文档不一致但产品确认新口径；记「观察项」，不计缺陷 |
| 数据问题 | 预置数据错误导致；修正数据后复测，不计产品缺陷 |

### 3.5 执行顺序

1. 冒烟（附录 C）→ 2. P0 模块 → 3. P1 模块 → 4. P2 模块 → 5. 异常/安全/兼容 → 6. 回归失败用例 → 7. 汇总报告。

### 5.3 复现与最小化

1. 每条缺陷至少复现 **3 次**；偶现问题记录「成功次数/尝试次数」。
2. 最小化步骤：去掉无关操作，只保留能触发问题的最短路径。
3. 明确「首次出现」的版本/提交；若无法确定，记录当前 HEAD。
4. 区分「必现」与「条件触发」（特定浏览器/特定数据/特定角色）。
5. 保存失败瞬间的 Network 请求与后端日志，尤其是 4xx/5xx。

### 5.4 去重与聚类

- 同一根因、不同页面表现 → 合并为一条，列出所有受影响入口。
- 同一接口导致的多处错误 → 以接口为主键合并。
- 同一文案/样式问题批量出现 → 可合并为一条「批量样式问题」，但需列出页面清单。
- 环境问题（后端未启动、AI key 缺失）单独归类为「环境阻塞」，不进入产品缺陷统计。

### 6.2 统计口径与公式

| 指标 | 公式 | 说明 |
|---|---|---|
| 执行率 | 已执行 / 用例总数 × 100% | 已执行 = PASS + FAIL + BLOCKED |
| 通过率 | PASS / 已执行 × 100% | 分母不含 SKIP |
| 缺陷密度 | 缺陷数 / 已执行用例数 | 可分等级统计 |
| 修复率 | 已修复 / 新增缺陷 × 100% | 报告截止时点 |
| P0 通过率 | P0 PASS / P0 已执行 × 100% | 必须 100% |
| 遗留严重缺陷 | S1 + S2 待修复数 | 发布门禁 |

### 6.3 结论判定标准

| 结论 | 条件 |
|---|---|
| 通过 | P0 用例 100% PASS；P1 通过率 ≥ 95%；无 S1/S2 遗留；核心链路（登录→人员→学期→课程导入→排课→作息→请假）全部通过 |
| 有条件通过 | P0 100% PASS；存在少量 S2 有明确规避方案且产品书面接受；或 S3 遗留不影响主流程 |
| 不通过 | 任一 P0 失败；存在 S1；存在无规避方案的 S2；核心链路中断 |

### 6.4 报告写作要求

1. **先结论后细节**：第 2 节直接给结论和阻断问题。
2. **数据可追溯**：每个统计数字都能在 `execution.csv` 中找到对应行。
3. **不掩盖失败**：FAIL/BLOCKED 必须写明原因与责任方（产品/后端/前端/环境/数据）。
4. **区分「未测」与「通过」**：未执行写 BLOCKED/SKIP，不写成通过。
5. **风险可执行**：每条风险给出规避方案或上线前必须完成的回归项。
6. **附证据索引**：报告正文提到的每个缺陷都要能定位到截图/接口/日志。
