# 课程聊天「可 @ 所有人」问题排查报告

> 排查时间：2026-10-09　范围：App（Android）+ 管理端（web-admin-react）+ 后端（backend）+ 数据库（init-db 全量导出）

## 一、结论

**不是权限配置错误，是数据模型缺陷**：课程聊天室的主键用的是**课程名字符串**（`chat_message.course_name`），而课程名**不是唯一的**——不同教师可以创建同名课程。于是：

- 李世易的「英语」聊天，@ 候选名单 = **全部 4 个同名「英语」课程所绑班级的并集 = 27 个班、1085 名学生（全校学生）**，而他自己只教 **1 个班、50 人**。
- 所以看起来"可以 @ 所有人"——确实是全校所有人。

**其他账号和课程：同样存在，且不止一个**（见第三节量化清单）。

## 四、同一根因连带的其他缺陷

因为房间键是课程名，以下功能**一起串号**（不是独立 bug）：

1. **聊天记录互相可见**：`GET /api/chat/{courseName}/public` 把 4 个「英语」班的消息合并展示——李世易能看到另外 3 位教师的师生对话，学生也能看到别班对话（**隐私泄漏**）。
2. **群发通知重叠**：`ScheduleNotifyService` 写入 `chat_message.course_name`，同名课程的通知/最后一条消息会互相覆盖与展示（`ScheduleService` L574/L582 查询同样按名）。
3. **未读数串号**：`ChatMessageMapper.markAsRead`、`/unread`、`/teacher/unread` 都按 `course_name` 统计。
4. **私发越界**：`parseMention` 全局按姓名匹配，配合上面的 @ 名单，可给非本课程学生发私密消息。
5. **App 端同样存在**：`ApiService.getChatMessages(token, courseName)` 与 `CourseDetailActivity` 的聊天室也是以课程名标识；学生端「英语」聊天同样会看到同名课程的消息。
6. **考勤等模块**：`CheckInController` 也有 6 处 `course_name = ?` 关联（需一并评估）。

## 五、修复建议

### 方案 A（推荐，彻底）：聊天室改用 course_id

1. `chat_message` 增加 `course_id BIGINT NULL` + 索引（`ALTER TABLE`），`course_name` 保留作展示。
2. 接口以 `courseId` 为房间键：`GET /api/chat/course/{courseId}`、`/send` 传 courseId，后端校验当前用户与该课程的班级/教师关系后再读写。
3. 迁移历史数据：能唯一确定的按 `course_name + class` 回填；无法判定的置空，查询时对 `course_id IS NULL` 的历史数据按旧逻辑兜底（一次性的过渡）。
4. 同步改：`getCourseStudents`（按 course_id + 归属校验）、`parseMention`（限定该课程班级内匹配；或直接由前端回传 `mentionUserId`）、未读数、排课通知、App 与管理端入参。
5. 优点：根治 4/5/6 项连带缺陷；缺点：改动面覆盖 后端 + 管理端 + App，需要一次 DB 迁移。

### 方案 B'（零迁移，快速止血）：约束课程名唯一

- 管理端创建/导入课程时校验同名冲突；
- 存量 18 组同名课程做数据治理（重命名为「英语(吕志远)」等）；
- 代码层同时把 `getCourseStudents` 的 SQL 加上教师归属收窄（`c.teacher_id = ?`）。
- 优点：不动表、不动客户端，半天可完成；缺点：治标，未来仍可能再出现同名；且课程名会带后缀。

### 无论选哪种，都建议顺手修掉

- `getCourseStudents`：课程定位改为 `course_name + teacher_id` 唯一化，不允许跨教师取名单（前端展示的 @ 名单立刻回到 50 人）。
- `parseMention`：把匹配范围限定到"该课程班级内的学生"，避免给非本课程学生发私密消息。
