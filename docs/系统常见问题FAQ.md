## 二、部署与环境

### Q2.1 后端启动失败，报 `Error starting ApplicationContext` / 数据库连不上

**现象**：IDEA 或 `mvn spring-boot:run` 启动直接报错退出，日志里有 `Communications link failure` 或 `Access denied for user`。

**可能原因**：

- MySQL 服务没有启动；
- 数据库名不是 `znxsglTest`（或没执行初始化脚本）；
- 账号密码与 `application.yml` 不一致（默认 `root/123456`，可用环境变量 `DB_USERNAME` / `DB_PASSWORD` 覆盖）。

**解决方案**：

1. 先确认 MySQL 已启动且端口 3306 正常：`mysql -u root -p` 能进入即可。
2. 执行初始化脚本建库建表：

   ```bash
   mysql -u root -p < init-db/znxsgltest.sql
   ```

3. 检查后端 `backend/src/main/resources/application.yml` 里的连接串是否与本地一致；不一致时优先通过环境变量覆盖，不要改代码：

   ```bash
   # Windows PowerShell
   $env:DB_USERNAME="root"; $env:DB_PASSWORD="你的密码"
   ```

> 注意：后端代码改动后需要在 IDEA 里**重启 ZnxsglApplication** 才能生效；前端 Vite 支持热更新，不用重启。

### Q2.2 管理后台页面打不开 / 后端接口 404

**现象**：浏览器访问管理后台白屏，或控制台请求 `/api/**` 全部 404。

**可能原因**：

- 后端没起来（先看 8080 端口）；管理后台请求的是后端接口，前后端需同时运行；
- 只启动了前端，没有启动后端。

**解决方案**：

```bash
# 后端
cd backend && mvn spring-boot:run      # :8080

# 管理后台（另开终端）
cd web-admin-react && npm install && npm run dev   # 默认 http://localhost:5174
```

管理后台通过 Vite 代理 `/api` `/uploads` `/ws` 到 `http://localhost:8080`，详见 `web-admin-react/vite.config.ts`。若代理目标写错，所有请求都会 404。

### Q2.3 Docker 部署后页面打不开

**现象**：服务器上 `docker compose up -d` 后，公网 IP 访问官网/管理端无响应。

**排查顺序**（按步骤执行）：

1. **阿里云安全组是否放行端口**：官网 `80`、管理端 `8081` 必须对 `0.0.0.0/0` 开放；`8080`/`3307`/`8000` 不建议对外。
2. 容器是否全部 Up：`docker compose ps`，若 `backend` 是 `Restarting`，看日志 `docker compose logs -f backend` 排查（通常是数据库未就绪或环境变量缺失）。
3. 用 IP 直接访问 `http://<服务器IP>:8081` 验证 Nginx 是否正常。

详细步骤见 [DOCKER_DEPLOY.md](../DOCKER_DEPLOY.md)。

### Q2.4 本地向量服务（Embedding）端口被占用 / 启动失败

**现象**：后端启动日志报 `8000 端口被占用`，或 `Embedding 服务启动失败`；AI 问答退化（不检索知识库）。

**可能原因**：

- 8000 端口已被其他进程占用；
- Python 环境缺少依赖，或 BGE-M3 模型目录不存在（首次需下载约 2.2GB）。

**解决方案**：

1. 临时关闭后端自动拉起，手动启动观察报错：

   ```yaml
   # application.yml
   embedding:
     local:
       auto-start: false
   ```

2. 手动启动：

   ```bash
   cd embedding-service
   pip install -r requirements.txt
   python start.bat          # 或 uvicorn main:app --port 8000
   curl http://localhost:8000/health   # 返回 ok 即就绪
   ```

3. 确认 `embedding-service/models/bge-m3` 目录存在；模型未下载时走镜像 `hf-mirror.com`。

> 即使向量服务挂了，系统也会**优雅降级**为关键词检索或直接凭大模型回答，不会导致 AI 功能完全不可用。

## 三、登录与权限

### Q3.1 登录成功但提示「无权限访问该资源」（403）

**现象**：账号能登录，但进入某功能（如章节管理、学习统计）时报 403，控制台显示 `无权限访问该资源`。

**可能原因**：`sys_user_role` 关联表为空或缺少该用户的角色关联，导致 RBAC 权限校验拿不到任何权限（例如缺 `chapter:view`），尽管 `user.role` 字段是正确的。

**解决方案**（一条 SQL 回填关联，按 `user.role` 映射：3→admin，2→teacher，1→student）：

```sql
INSERT INTO sys_user_role (user_id, role_id)
SELECT u.id,
       CASE u.role WHEN 3 THEN 1 WHEN 2 THEN 2 ELSE 3 END
FROM user u
WHERE NOT EXISTS (SELECT 1 FROM sys_user_role r WHERE r.user_id = u.id);
```

修复后**无需重启后端**，用户重新登录即可生效。

> 经验：`user.role`（1学生/2教师/3管理员）是业务粗粒度角色；`sys_role`/`sys_user_role` 是细粒度 RBAC。两者都要正确，缺一就会出现「能登录但没权限」。

---

### Q3.2 提示「账号或密码错误」，但数据明明在

**可能原因**：密码以**明文或 MD5** 存储，而系统登录校验走 **BCrypt**（项目约定密码必须 BCrypt 哈希，MD5 不支持）。

**解决方案**：用系统自带的初始化逻辑重新加密。项目在 `DataInitializer` 中实现了启动时密码修复（将明文/MD5 统一转为 BCrypt）。若仍有账号无法登录：

1. 重启后端触发一次初始化修复；
2. 仍不行则手动在数据库把该账号密码改为 BCrypt 值，或删除该行让初始化逻辑重建。

---

### Q3.3 Token 过期 / 重新登录后一直跳回登录页

**说明**：JWT 默认有效期 `604800000ms`（7 天），过期后需重新登录。本地开发可在 `application.yml` 临时调大 `jwt.expiration`。生产环境建议维持 7 天并通过环境变量 `JWT_SECRET` 注入自定义密钥（要求 ≥32 字节）。

## 四、AI 服务与 RAG

### Q4.1 AI 不回复 / 回复为空 / 提示「AI 服务繁忙」

**排查顺序**：

1. **API Key 是否已配置**：`llm.api-key` 来自环境变量 `DEEPSEEK_API_KEY`（**没有内置兜底值**）。未配置时 AI 功能整体不可用，其余功能正常。
   - Windows PowerShell 永久设置：
     ```powershell
     [Environment]::SetEnvironmentVariable("DEEPSEEK_API_KEY","sk-你的Key","User")
     ```
   - IDEA 运行配置 → Environment variables 也可临时注入。
2. **网络是否可达 DeepSeek**：`llm.url` 默认 `https://api.deepseek.com/chat/completions`，需要能访问外网。
3. **看后端日志**：
   - `=== LLM 错误[4xx/5xx]` → Key 无效或余额不足，去 DeepSeek 平台核对；
   - `=== LLM 调用超时` → 网络慢或 prompt 太长（出题 prompt 已截断到 4000 字符内）；
   - `RateLimitException` → 触发限流，见 [Q11.1](#q111-报ai服务繁忙或请求过于频繁)。

---

### Q4.2 AI 回答像「瞎编」，没有用上传的课程资料

**原因**：RAG 依赖 `document_vector` 表里有该课程的向量数据。回答前系统先检索知识库（余弦相似度 top-5，阈值 0.3），检索不到就降级为「凭大模型自身知识回答」。

**解决方案**：

1. 确认该课程内容已入库：先上传/生成课程文档或章节，并确认向量化成功（`document_vector` 对应记录 `embedding` 非空）。
2. 确认 Embedding 服务在运行（见 [Q2.4](#q24-本地向量服务embedding-端口被占用--启动失败)）；服务挂了系统会静默降级，表现为「回答质量差但不断线」。
3. 提问时带上课程语境；课程群聊里只有消息带 **@AI** 才会触发 RAG 回答，普通消息不触发。

---

### Q4.3 上传文档后 AI 说「暂不支持的文件类型」/「未能提取到文字内容」

**说明**：支持 `PDF / DOCX / DOC / TXT / MD`。原因排查：

- 文件是图片型 PDF（扫描件）或加密文档 → 无法提取文字；
- `.doc`（老格式）走 AI 分析，可能不稳定；
- 分块规则：按 500 字/块，每批 ≤25 条，超过会被截断。

建议：优先上传可复制文字的 PDF/DOCX/TXT；扫描件请先转成文字版。

---

### Q4.4 换模型 / 换 API 地址怎么改

在 `backend/src/main/resources/application.yml`：

```yaml
llm:
  api-key: ${DEEPSEEK_API_KEY}
  model: deepseek-v4-flash        # 当前使用的低成本模型
  url: https://api.deepseek.com/chat/completions
```

只要接口兼容 OpenAI Chat Completions 格式，改这三项即可切换。当前使用 `deepseek-v4-flash`，成本约为高级模型的 1/3，并发额度更高。

## 五、刷题与测评

### Q5.1 点「开始刷题」转圈没反应 / 提示「请先学习章节内容再答题」

**说明**：出题范围 = 学生**已完成阅读的章节**（`chapter_read_progress` 有记录）。必须先学习该课程章节，才能出题。

**解决方案**：

- App/小程序：先进入课程 → 阅读对应章节（课时），再回专注刷题页开始；
- 若已读章节仍报此错，检查 `chapter_read_progress` 表是否有记录，或阅读后下拉刷新再试。

---

### Q5.2 点「开始刷题」长时间转圈 / 提示「出题任务已过期，请重新开始」

**原因**：出题是**异步流程**：`POST /api/quiz/generate` 立即返回 `taskId`，App 每 2 秒轮询 `GET /api/quiz/generate/result`。以下情况会失败：

- 没学过章节 → 任务直接 error；
- Embedding 服务挂了导致章节内容取不到 → error「章节内容尚未准备好」；
- AI 调用超时（180s）或返回无法解析 → error「题目生成失败」；
- 任务结果只保留 **10 分钟**，超过后轮询会返回「任务已过期」。

**解决方案**：按上面的原因逐项排查（先读章节、保证 Embedding 在运行、保证 `DEEPSEEK_API_KEY` 有效）。后端日志搜 `=== AI出题原始返回` / `=== 后台出题异常` 定位具体失败点。

---

### Q5.3 提交测评后没有六维评估结果（只有对错）

**说明**：客观题立即判分；**主观题（解析/填空）**由 AI 语义判分，评估结果由 AI 生成（六维分数、强弱项、学习计划）。AI 失败时降级逻辑：

- 主观题 → 字符 bigram 相似度（Dice ≥0.35）兜底判分；
- 评估 JSON → 解析失败则跳过（分数显示为 0，不报错）。

**解决方案**：看后端日志 `=== AI评估返回` / `=== 主观题AI判分返回` 是否为 null；为 null 说明 AI 调用失败（Key、限流、超时），修复后重新做一次测评。

---

### Q5.4 错题解析一直「生成中」/ 转圈

**说明**：错题解析接口（`/api/quiz/wrong-analysis`）有**缓存**：错题数未变化时直接返回缓存结果；单次最多分析 30 道错题，超出部分截断。AI 失败时各题分析显示「（分析生成中）」。

**解决方案**：

- 稍后重试（AI 临时繁忙），或先「标记明白/收藏」减少错题数再分析；
- 后端日志搜 `=== AI错题解析返回`，为 null 时查 Key/限流/超时。

---

## 六、排课与课表

### Q6.1 排课结果不显示 / 课表空白

**排查**：

1. 一键排课前必须先配置学期（如 `2026-2027-1`），否则排课任务没有目标学期；
2. 确认 `schedule` 表已生成记录（排课后按班级查）；
3. 学生 App 课表基于 `schedule` 表 + 学生所在班级的课程关联生成，班级与课程要有关联（`course_class` 表）。

---

### Q6.2 周日课程不显示 / 手动排到周日不生效

**说明**：系统支持周日排课（`dayOfWeek=1-7`，1=周一，7=周日），用于节日补课场景。

- **管理端调课窗口**显示 7 列（含周日）；
- **周日课程导入**和**周日排课**需要在**后端重启后**才完全生效（含周日的课程导入需先重启后端）；
- **App 端**需要重新构建安装 APK 才能看到周日列；
- 管理端刷新页面后调课窗口显示周日列。

---

### Q6.3 调课操作后课表没变化

**说明**：调课走「取消源时段 + 目标时段重排」的事务流程。检查：

- 调课后必须点**确认**（触发事务性 delete/create）；
- 跨周移动：先取消源周格子 → 切换到目标周 → 选择新格子 → 确认；
- 排课记录按周拆分存储，改的是对应周次的记录。

---

### Q6.4 教室容量不足

**说明**：排课算法优先匹配容量充足的教室，不足时**自动回退使用普通教室**。若希望严格限制，请调整 `classroom` 表的 `capacity` 数据后重新排课。

---

### Q6.5 自动排课只排周一到周五

**说明**：一键排课算法仅自动排周一至周五（`dayOfWeek=1-5`），不会自动排到周末；周日的课需要**手动排课**（导入或调课窗口手动添加）。

---

## 七、聊天与通知

### Q7.1 聊天消息收不到 / 日志报 `WebSocket sendToUser 无session`

**原因**：WebSocket 推送依赖接收方当前**在线**（已建立 `ws://host/ws/schedule?userId=xxx&role=xxx` 连接）。日志 `=== WebSocket sendToUser 无session: userId=...` 表示该用户当前没有在线连接，消息已**放弃推送**（不是排错）。

**解决方案**：

1. 确认接收方（学生/教师）App 已登录且网络正常，WebSocket 已连上（后端日志应有 `WebSocket 学生连接: userId=...`）；
2. 教师端：教师页面打开后即建立 WebSocket，切换页面会断开，回到页面会重连；
3. App 退到后台/断网后，需要回到前台自动重连；
4. **兜底方案**：聊天记录都落库（`chat_message` 表），刷新/重新进入聊天页会从数据库拉取，消息不会丢，只是推送不及时。

---

### Q7.2 消息重复推送 / 通知重复

**说明**：系统内置两级去重：

- **用户级推送去重**：60 秒内同一用户同一类型相同内容只推送一次（`ScheduleWebSocketHandler`）；
- **调课操作级去重**：以「课程:班级:原时段->新时段:教室:原因」为 key，5 分钟内同一操作只发一次通知。

出现重复通常是**多端同时在线**（App + 小程序 + 管理端）各推一次。属正常现象，不影响数据。

---

### Q7.3 图片 / 文件发出去别人看不到

**排查**：

1. **路径问题**：后端返回的图片 URL 若含 `http://localhost:8080` 或相对路径，App 端通过 `RetrofitClient.toFullUrl()` 自动修正（替换为当前 BaseUrl）。若你自己改了 BaseUrl（真机调试），图片 URL 也会跟着指向新地址，确认后端可达。
2. **权限问题**：`/uploads/**` 和 `/api/chat/download-file` 已在安全白名单（匿名可访问）。若改过 `SecurityConfig`，需把这两个路径加回白名单，否则图片 403。
3. 文件大小限制：上传最大 **20MB**，超出会被拒绝。

---

### Q7.4 教师铃铛通知异常

**常见现象与处理**：

| 现象 | 原因 / 处理 |
|------|------------|
| 提示了教师自己发的消息 | 通知过滤逻辑已排除 `sender_role=teacher` 且发送者为本人的消息；仍出现时确认教师端代码是最新版本 |
| 在当前聊天窗口还提示该课程消息 | 前端已过滤「正在查看的课程」的通知；切换窗口后仍提示，请刷新页面 |
| 点击通知后红点不消失 | 正确流程是：点击后**立即**从本地列表移除该课程全部未读提示，并调用后端标记已读，再跳转聊天页。若未生效，检查通知点击回调是否先清本地再发请求 |

---

### Q7.5 AI 不回答聊天消息

**说明**：聊天默认**正常发送**，只有消息内容包含 **@AI** 或 **@ai** 时才会触发 AI 回复（RAG 检索 + 大模型生成）。这是刻意设计，避免每条消息都消耗 AI 额度。

## 八、考试与作业

### Q8.1 学生端看不到考试/作业，或显示「暂不可作答」

**说明**：学生端考试作业入口展示**所有已发布且未结束**的考试作业，与开始时间无关。

- `status=1`（已发布）且学生未提交 → 正常作答；
- 未发布 / 已结束 / 已提交 → 显示「暂不可作答」或「已完成 · X分 / 查看详情」；
- 不可作答的条目**点击后弹友好提示**，不会跳转闪退。

---

### Q8.2 学生作答提交后成绩不对 / 得分显示错误

**排查**：

1. 得分展示曾出现过 `Badge` 组件 `variant` 值写错（`"destructive"` 应为 `"danger"`）导致样式/数值异常，已修复；若仍异常检查前端版本。
2. AI 出题模式（`question_mode=ai-range` / `ai-document`）下，题目由 AI 生成，主观题自动判分结果可能偏松/偏严；可在成绩详情查看 AI 评分与评语（`exam_sub_answer` 表 `ai_score`/`ai_comment`）。

---

### Q8.3 考试通知重复推送 / 学生收不到考试通知

**说明**：考试/作业通知实现了**三重去重**：内存缓存（10 分钟 `examId_userId`）、数据库预检查、唯一索引 `uk_user_biz(user_id, biz_type, biz_id)`（`chat_message` 表）。若出现重复或丢失：

- 查 `chat_message` 表该学生该考试的记录是否存在（唯一索引会拦截重复插入）；
- 通知走 WebSocket 推送，离线学生收不到推送（但记录在库，登录后可从通知列表看到）。

## 九、数据导入

### Q9.1 Excel 导入失败 / 提示表头不合法

**说明**：不同导入功能有不同的表头规范：

| 功能 | 表头要求 |
|------|----------|
| 学生批量导入（管理端） | 必须包含 **「学号」和「姓名」** 列；仅支持学生，教师名单会被拒绝并提示 |
| 课程导入 | 必须包含课程名、班级、教师、每周课时等字段；周次字段取值 1-7（含周日） |
| 课表导入 | 输入已含时间/地点/教师的现成课表，系统只做识别抄录 |

**常见失败原因**：表头字段名与规范不一致、行数超 1000、班级不存在、用户名重复、文件超过 10MB 或非 `.xlsx/.xls`。详细规范见 [schedule-import-spec.md](schedule-import-spec.md) 与 [course-chapter-import-plan.md](course-chapter-import-plan.md)。

---

### Q9.2 导入成功但没有反馈 / 页面没刷新

**说明**：批量导入流程有完整视觉反馈：导入期间**全屏遮罩 + 加载动画**，结束后显示成功/失败横幅（总数、成功数、跳过数、错误明细），结果缓存在 `sessionStorage`（30 分钟），并仅在成功 ≥1 条时才刷新列表。

若没看到反馈，检查浏览器是否拦截了弹窗/动画，或看后端日志导入接口是否报错。

---

### Q9.3 课程导入后状态 / 学生课表没变化

**说明**：课程导入成功后自动置为**上架**（`status=1`），并**立即为学生生成 schedule 记录**。若学生 App 课表没显示：

1. 确认课程确实上架（课程管理里 status=1）；
2. 确认学生所在班级与课程已关联；
3. 学生端需**下拉刷新或重新进入**课表页；
4. 含周日的导入需重启后端（见 [Q6.2](#q62-周日课程不显示--手动排到周日不生效)）。

## 十、多端联调

### Q10.1 App 连不上后端

**说明**：Android 端 BaseUrl 在 `RetrofitClient.getBaseUrl()`：

- **模拟器**：`http://10.0.2.2:8080`（自动映射宿主机 localhost，IP 变化不影响）；
- **真机**：改为电脑局域网 IP，如 `http://192.168.10.8:8080`（DHCP 重新分配后需同步修改）；
- **部署服务器**：改为公网地址 `http://<服务器IP>:8080`。

改完后需**重新构建安装 APK**。真机与电脑需在同一 Wi-Fi 网络。

---

### Q10.2 真机/模拟器上图片、文件加载 404

**排查**：

1. 后端是否可访问（先确认 Q10.1 的 BaseUrl）；
2. 图片 URL 拼接：App 已做 `toFullUrl` 兼容处理（历史数据里的 `localhost` 会被替换），确认用的最新包；
3. 服务端 `uploads` 目录是否存在对应文件；管理端/后端若换过目录，旧数据指向的文件可能不存在。

---

### Q10.3 管理后台 / 小程序功能与 App 不一致

**说明**：三端共用同一套后端接口。若某端功能缺失，优先确认该端代码是否最新（管理端 Vite 热更新、小程序需重新编译上传、App 需重新构建）。App 与后端接口改动需要**同时更新**，否则会因字段不匹配报错。

## 十一、性能与高并发

### Q11.1 报「AI 服务繁忙」/「请求过于频繁」

**说明**：AI 调用有双重限流：

- **全局限流**：每秒最多 20 次（`RateLimiter.create(20.0)`）；
- **单用户限流**：每分钟最多 10 次。

**交互式场景**（聊天、错题分析）超限会直接拒绝并提示「请稍后再试」。这是**防滥用保护**，不是故障。

---

### Q11.2 几十人甚至 100 人同时刷题会不会卡死

**说明**：已经过异步化改造，设计目标就是支撑 100 人同时出题：

- **异步出题**：`POST /api/quiz/generate` 立即返回 `taskId`，不占用 Tomcat 线程，前端轮询结果；
- **固定线程池**：20 线程排队执行出题任务，超出时排队而非拒绝；
- **排队式 AI 调用**：`chatQueued()` 用 `RateLimiter.acquire()` **阻塞等待令牌**而不是直接拒绝，高并发时请求自动排队（平均等待约 50ms），保证所有人都能拿到结果（先后不同而已）；
- **出题缓存**：同课程+难度+科目+题型+已学章节的 MD5 指纹缓存 **15 分钟**，同档位学生并发时只调一次 AI，其余命中缓存，峰值 AI 调用量降低 70% 以上。

**结论**：正常情况不会卡顿；若单用户连续触发「请求过于频繁」，是 10 次/分钟的单用户限流在起作用。

---

### Q11.3 多线程出题会不会把数据库打爆

**说明**：Hikari 连接池默认 `maximum-pool-size=20`，与出题线程池 20 一致；出题任务内数据库操作量小（查询难度/章节/写 session），且评估/难度更新失败均不影响主流程（try-catch 包裹）。若仍担心，可调低 `spring.datasource.hikari.maximum-pool-size`。

---

### Q11.4 App 端刷题闪退

**历史问题**：Android 11+ 上 `FullscreenLoaderDialog` 在调用 `getInsetsController` 前未创建 DecorView，导致 NPE 闪退。**已修复**（强制 `window.getDecorView()`）。若仍闪退，确认使用最新 APK，并看 Logcat 崩溃堆栈定位新的原因。

## 十二、数据库与数据安全

### Q12.1 数据备份与恢复

```bash
# Docker 部署环境
docker run --rm -v znxsgl_mysql_data:/data -v $(pwd):/backup alpine tar czf /backup/mysql_backup.tar.gz /data

# 本地环境
mysqldump -u root -p znxsglTest > znxsglTest_$(date +%Y%m%d).sql
```

### Q12.2 密码 / 敏感配置管理

- 密码一律 **BCrypt 哈希**存储，数据库里不该出现明文或 MD5；
- `DEEPSEEK_API_KEY`、数据库密码、`JWT_SECRET` 必须走**环境变量**，严禁硬编码进 `application.yml` 或代码；
- 若密钥曾进入 Git 历史：先在 DeepSeek 平台重置密钥，再清理 Git 历史后重新推送。

### Q12.3 误删数据 / 想清空业务数据重来

**说明**：项目提供清理脚本（删除 `course`、`schedule` 表数据以清空旧业务数据）。清理前先**备份**。注意：删除课程会连带删除该班学生的排课记录、课程-班级关联及专属课程数据；公共课（其他班级在用）保留。

### Q12.4 WebSocket / 通知历史数据

通知与聊天记录都存在 `chat_message` 表。清理旧通知时系统内置规则：插入新通知前删除该课程该学生所有 `sender_role='teacher'` 且内容含【课程通知】/排课已更新/课程「开头 的旧通知，避免表无限膨胀。

## 十三、日志排查指引

后端日志分两个文件：`backend/backend.log`（常规）、`backend/backend-live.log` / `backend-live.err`（运行期）。

| 想查什么 | 搜什么关键字 |
|----------|--------------|
| 登录 / Token 问题 | `JWT`、`认证`、`403` |
| AI 调用 | `=== LLM 请求`、`=== LLM 回复`、`=== LLM 错误`、`=== LLM 调用超时` |
| 出题流程 | `=== 出题缓存命中`、`=== AI出题原始返回`、`=== 后台出题异常` |
| 测评评估 | `=== AI评估返回`、`=== 主观题AI判分返回`、`=== 错题解析` |
| WebSocket | `WebSocket 连接`、`WebSocket 断开`、`=== WebSocket sendToUser`、`被用户级去重拦截` |
| 排课通知 | `=== WebSocket sendToClass`、`通知去重`、`ScheduleNotifyService` |
| 数据库问题 | `Communications link failure`、`SQLSyntaxErrorException`、`Deadlock` |

**通用排查五步**：

1. 复现问题并立即查看对应日志关键字；
2. 先查**环境**（Key、端口、MySQL、Embedding）再查代码；
3. 后端改动 → 重启 ZnxsglApplication；前端改动 → 刷新页面（App 需重新构建）；
4. 权限类问题先查 `sys_user_role` 是否缺失（见 [Q3.1](#q31-登录成功但提示无权限访问该资源403)）；
5. 拿不准时，把日志关键字 + 报错原文提供给开发者定位。
