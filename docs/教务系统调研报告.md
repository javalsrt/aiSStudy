# 教务系统调研报告：传统系统与优秀系统的特点对比

> 调研时间：2026-11
> 调研目的：梳理高校教务系统的业务全景、传统系统的典型问题、优秀系统的共性能力，为 aiStudy（智学职达）的课程/排课/考勤/学情模块设计提供参照。
> 资料性质：厂商官网产品页、行业盘点文章、产品设计文章、国际 SIS 产品文档、教育部规范、学生侧真实吐槽。
> **可信度提示**：厂商页面的量化指标（效率提升 xx%、并发 xx 万）均为自述、无第三方验证；部分行业分析文章为 AI 生成/SEO 内容，仅作观点参考，不作事实依据。

## 一、教务系统到底在管什么

### 1.1 业务主链路

```
招生录取 → 学籍建档 → 培养方案 → 开课计划/教学任务 → 排课 → 选课
                                                    ↓
        毕业审核 ← 成绩管理 ← 考务安排 ←──────────────┘
                ↓
        教学质量评估 / 报表上报 / 学业预警
```

### 1.2 角色与诉求差异

| 角色 | 核心诉求 | 典型行为 |
|---|---|---|
| 学生 | 少折腾、结果确定、手机能办 | 选课、查课表、查成绩、申请异动 |
| 教师 | 少重复录入、课表清晰 | 接教学任务、录成绩、调课 |
| 院系教务员 | 批量处理、少核对 | 排课、审核、汇总 |
| 教务处 | 规则可配、数据可信、可上报 | 培养方案、监控、报表 |
| 校领导 | 趋势与风险可见 | 看板、预警 |

### 1.3 系统形态三分

| 形态 | 代表 | 特点 | 代价 |
|---|---|---|---|
| 套装软件 | 正方、强智、青果、清元优软 | 功能全、案例多、稳定 | 定制贵、迭代慢 |
| SaaS | 各类云教务 | 上线快、按年付费 | 流程固化、数据在校外 |
| 低代码/自研 | 高校自建平台 | 贴合本校、可迭代 | 依赖自身团队 |

> 关键判断：教务系统的本质是「**强规则 + 强流程 + 周期性洪峰 + 强合规**」的业务系统，不是内容产品。它的难点不在页面，而在规则表达能力和峰值稳定性。

## 二、传统教务系统的典型特点

### 2.1 架构层面

1. **单体 + 服务端渲染**：前后端不分离，页面必须先等数据库返回才能渲染，任何慢查询都直接放大为"白屏"。
2. **认证靠 CAS 拼接**：各子系统独立建设，只用单点登录串起来，没有统一身份与权限治理 → 认证中心一旦阻塞，**单点登录变成单点故障**，全链路瘫痪。
3. **选课高峰靠数据库硬扛**：选课本质是对"课程余量"字段的高频争抢写，缺少缓存、队列、限流，直接形成**行锁竞争**，表现为 504 / "访问人数过多"。
4. **批处理同步**：模块间靠定时任务对数据，天然存在延迟窗口（欠费仍可选课、休学仍被排考）。

### 2.2 功能与流程层面

5. **按科室切分功能**：菜单是"培养方案管理 / 排课管理 / 成绩录入"，对应教务处内部编制；而学生的任务是"我要毕业、我要选课"，两者错位。
6. **核心逻辑是审批与留痕，不是洞察**：系统设计目标是防错、可追责，因此到处是审批节点和状态机，缺少推荐、预警、解释。
7. **规则写死在代码里**：学分制改革、微专业、跨学科项目制课程一落地就要二次开发，周期数月，学校只能妥协成"简化版方案"或退回纸质审批。
8. **极端场景能力弱**：超大规模并发选课、多约束排课（连堂、合班、单双周、场地容量、教师不可用时间）往往靠人工兜底。

### 2.3 数据层面

9. **烟囱式数据**：教务、学工、一卡通、图书馆各建各库，物理同网、逻辑隔绝。
10. **数据只作事务记录**：成绩就是成绩，不沉淀为画像；学业风险只能事后通报，无法事前介入。

### 2.4 体验层面

11. **PC 优先**：移动端通常只做到"查课表"，选课、调课、申请仍必须回电脑。
12. **术语导向**：界面写"教学任务安排""培养方案异动"，学生看不懂；缺少空状态、失败原因、下一步引导。
13. **状态反馈缺失**：没有排队位次、没有提交回执、没有结果通知，"选课结果薛定谔"。
14. **无无障碍设计**：键盘操作、对比度、屏幕阅读器基本不考虑。

### 2.5 学生侧的真实抱怨（高频）

- 抢课=抽奖：整点崩溃、刷新后名额已满、热门课秒光。
- 课程介绍形同虚设：只有课名和学分，不知道谁上、考什么、给分如何。
- 冲突提示滞后：选上了才发现与必修课时间重叠。
- 结果不可回滚：误操作后无法撤销，只能找教务员。

## 三、优秀教务系统的共性能力

可以把"优秀"拆成六层能力模型，任何一层缺失都会在真实使用中暴露。

### L1 业务闭环与规则可配置

- 覆盖 **招生 → 学籍 → 培养方案 → 排课 → 选课 → 考务 → 成绩 → 毕业审核** 全链路，模块间数据自动流转。
- 培养方案做成**参数化模型**（学分、学时、授课模式、课程矩阵），支持"培养方案—课程体系—毕业标准"三级映射与**版本留痕**。
- 规则引擎承载绩点换算、补考/重修/免修/等级折算、毕业资格判定，改规则不改代码。
- 支持非标准学制：并行校历、本研贯通、微专业、可叠加证书（stackable credentials）、跨学科项目。

### L2 架构与峰值稳定性

| 关注点 | 做法 |
|---|---|
| 削峰 | 消息队列异步排队、令牌/预约制选课、错峰分批开放 |
| 读加速 | 余量走 Redis、读写分离、多级缓存 |
| 写安全 | 预扣减 + 幂等令牌 + 最终一致性落库，避免行锁争抢 |
| 弹性 | 微服务多实例、容器化水平扩容，开学季按需扩 |
| 降级 | 网关限流熔断，先保登录与查询，非核心功能可降级 |

> 现实标杆：厂商宣称微服务集群可承载 5 万+ 选课洪峰；国际产品强调"任意设备、几次点击完成注册"。

### L3 数据贯通

- **统一数据模型 + 主数据**：学生、课程、教学班、教师、场地的唯一事实源。
- **事件驱动**替代定时批处理：排课变更 → 课表/考勤/通知自动联动。
- **全链路可追溯**：培养方案 → 课程 → 教学班 → 排课 → 成绩 → 毕业审查，任一环变更自动重算。
- 数据资产化：学分完成度、成绩趋势、课程分布形成学生画像，支撑预警与个性化。

### L4 智能化（用在刀刃上）

- **AI 排课**：约束满足 + 校本历史数据，支持上百条规则（连堂、合班、单双周、场地容量、教师偏好），毫秒级全域冲突检测，"一键生成 + 人工微调"。
- **AI 排考**：师资—场地—时间三维避障，分钟级出方案。
- **学业预警**：「能力达成 + 修读进展」双主线，可视化呈现学分缺口、成绩下滑趋势。
- **智能问答**：把"教务政策问答"做成入口，降低咨询成本。
- **AI 辅助审核**：成绩异常、材料合规的初筛，人工只做终审。

### L5 体验设计

- **任务导向的信息架构**：首页不是功能菜单，而是"待办 + 本周课表 + 风险提醒"。
- **移动优先、全流程可办**：选课、请假、评教、查成绩都在手机完成，PC 只是增强。
- **确定性反馈**：候补位次、排队进度、提交回执、变更推送，让学生知道"现在到哪一步了"。
- **前置校验**：选课前直接显示"是否具备资格 / 是否冲突 / 还缺什么先修课"。
- **可控感**：已选课程可撤销、课表可模拟（保存方案，开放时一键提交）。
- **无障碍与低学习成本**：少术语、有引导、有示例。

### L6 治理与生态

- 开放 API / 标准接口，能被门户、小程序、第三方工具调用，而不是再造一个入口。
- 低代码/表单流程引擎，让教务员自己改审批流与字段。
- RBAC + 数据范围（校级/院系/班级）+ 操作审计日志。
- 等保合规、私有化部署选项、数据所有权归学校、SLA 与灾备写进合同。
- 关注 **TCO**：许可 + 实施 + 硬件 + 运维 + 二次开发 + 培训，而非只看采购价。

## 四、传统 vs 优秀：十维对照

| 维度 | 传统系统 | 优秀系统 |
|---|---|---|
| 设计起点 | 教务处科室分工 | 用户任务与学习路径 |
| 核心逻辑 | 审批、留痕 | 洞察、匹配、预警 |
| 架构 | 单体、SSR、CAS 拼接 | 微服务、前后端分离、统一身份 |
| 峰值 | 数据库硬扛，整点崩溃 | 预约/错峰/队列/缓存，平稳 |
| 规则 | 写死在代码 | 规则引擎 + 参数配置 + 版本管理 |
| 数据 | 烟囱、批处理同步 | 统一模型、事件驱动、全链路贯通 |
| 智能 | 近乎空白 | 排课排考、学业预警、智能问答 |
| 终端 | PC 优先 | 移动优先，全流程可办 |
| 反馈 | 无排队、无回执 | 位次、进度、推送、可撤销 |
| 扩展 | 二次开发数月 | 开放 API + 低代码 |

## 五、怎么判断"好不好"：可量化指标

不只看功能清单，看四类硬指标。

**性能与稳定**
- 选课峰值并发、P95 响应时间、请求成功率、故障恢复时间（RTO）。

**业务效率**
- 一次排课的人工投入（人日）、成绩录入到发布的时长、审批平均时长、毕业审核差错数。

**数据质量**
- 跨系统接口调用量 ÷ 人工导出量（越高越好）、数据不一致条数、预警命中率。

**体验与采纳**
- 移动端可办业务占比、任务一次完成率、师生满意度/NPS、培训成本。

> 教育部《高等学校数字校园建设规范（试行）》给出的建设原则可直接作为评价框架：**应用导向、数据驱动、注重融合、体验优先、安全可靠、适度超前**；应用服务要求"以用户为中心实现集成、融合与扩展，支持跨领域业务协同，实现一站式办理"，并明确"在事务处理型系统之外应加强分析型应用"。

## 六、对 aiStudy 的启示

### 6.1 现状定位

aiStudy 已覆盖：课程管理、课表排课、考勤签到、学习统计、AI 答疑、专注训练，多端（React 管理后台 / 小程序 / Android），并且**已有** `AutoScheduleService`（自动排课）、`ScheduleConflictChecker`（冲突检测）、`ScheduleRule`（排课规则）、`ScheduleLock`（锁课）等能力——在"排课"这一环已经超出多数传统教务系统的实际交付水平。
对应教务主链路的 **开课 → 排课 → 考勤/成绩 → 学情** 一段，与"完整教务系统"是子集关系。**不建议**为了"像教务系统"而补学籍异动、招生、财务、毕业审核——那是另一套合规与流程体系，投入产出比低。

### 6.2 值得优先做的四件事

1. **模型分层：`Course` 与"教学班"分离**（优先级最高）。
   现状 `course` 直接持有 `teacherId` + `semester`，`schedule` 以 `userId` 维度存课表并冗余 `courseName`，等价于"一个学生一条排课记录"。后果是：同一门课换学期要复制课程、统计口径按人而非按班、成绩与考勤无法挂到"班"上。
   建议拆成 `Course`（课程目录：名称/编号/学分/简介）→ `Section`（教学班：学期 + 教师 + 容量 + 上课安排）→ `Enrollment`（选课关系），`schedule` 只保留"班 × 时间"的排课事实。
2. **把冲突检测从"能查"做到"能解释"**：现有检查器已能判冲突，优秀系统的差异在于**告诉用户和哪门课、哪个教室、哪位教师冲突，以及可行的替代方案**。规则可配置（连堂、单双周、场地容量）比算法更影响落地。
3. **峰值链路**：签到、锁课/选课类写操作，Redis 预扣减 + MQ 异步落库 + 幂等键，避免直接打 MySQL 行锁；管理端已有 WebSocket 通知，可扩展为"变更推送"。
4. **任务中心化首页**：学生端首屏给"今日课表 + 待办（签到/作业）+ 学习风险提示"，而不是功能宫格。

### 6.3 AI 的落点

优先级从高到低：**学业预警（数据已有，价值最高）→ 课程/资源推荐（有行为数据）→ 智能问答（已有）→ 排课优化（规则复杂，收益靠规模）**。
避免把 AI 做成聊天入口的装饰，先保证"预警能被人看到并触发动作"。

### 6.4 可复用的选型/设计清单

- 表单 + 流程引擎的自定义能力，决定系统能活多久。
- 每个列表页都要有：空状态、失败原因、批量操作、导出。
- 每个写操作都要有：二次确认、结果回执、可撤销窗口。
- 每个跨模块变更都要问一句：谁需要被通知？哪张表需要重算？
